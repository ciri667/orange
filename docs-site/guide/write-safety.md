# 写入确认机制

橘记最重要的安全设计：**Agent 不能直接改你的文件。**

## 完整链路

```
┌─────────────┐   ┌──────────┐   ┌────────────┐   ┌──────────┐   ┌──────────┐
│ 生成 diff   │ → │ 路径校验 │ → │ hash 校验  │ → │ 用户确认 │ → │ 原子写入 │
└─────────────┘   └──────────┘   └────────────┘   └──────────┘   └──────────┘
```

1. **生成 diff** — Agent 调用 `edit` 或 `write`，产生一个待审阅的变更，此时磁盘上什么都没变。
2. **路径校验** — 目标路径必须在当前会话授权的知识库范围内；受保护的系统目录会被拒绝。
3. **hash 校验** — 确认写入前重新计算文件内容 hash，确保你审阅的 diff 和即将写入的内容一致。文件在这期间被别的程序改过，写入会失败而不是覆盖。
4. **用户确认** — 你在 diff 界面里确认或拒绝。
5. **原子写入** — 确认后才真正落盘，写入过程是原子的，不会留下半个文件。

## 你会看到什么

- 变更以 diff 形式展示，可以逐处查看新增和删除。
- 一次会话里的多处改动会合并成一个变更集，可以整体审阅。
- 拒绝则整份变更作废，文件保持原样。

## 换行符与 BOM

`edit` 的匹配逻辑容忍 CRLF 和 UTF-8 BOM：

- 你可以放心传入 LF 换行的片段。
- 写入时会保留原文件的换行符和 BOM，不会因为一次编辑把整个文件的换行风格改掉。

## `edit` 的三种操作

| 操作 | 用途 |
| --- | --- |
| `replace` | 替换一个**唯一**的片段；片段重复时可用 `occurrence` 指定第 N 处 |
| `append` | 在笔记末尾追加（增量内容会 trim，Markdown 会用空行分隔） |
| `multi_replace` | 一次 diff 里做多处唯一替换 |

## `write` 的两种形态

| 类型 | 说明 |
| --- | --- |
| `kind=file`（默认） | 新建 Markdown / TXT 文件，必须提供完整正文和知识库相对路径 |
| `kind=folder` | 新建文件夹；基础级别会话不允许 |

::: tip 为什么要求「完整正文」
基础 / 进阶级别要求模型给出完整内容，只是把落盘推迟到你确认。这样你审阅的就是最终文件，而不是一段增量。
:::

## 完全级别的例外

在 `autonomous`（完全）级别下，校验通过后会**自动落盘**，不再中途打断你。路径校验和 hash 校验仍然执行。

如果你希望每一次改动都由自己确认，请保持基础或进阶级别。
